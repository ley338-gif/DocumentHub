# Public Access

Unauthenticated pages reachable from a printed/engraved QR code (spec
§29-32, §48, §50). Implemented in `apps/api/src/public/`. These routes carry
no `X-Organization-Id` header and no JWT — org context comes entirely from
the stable ID embedded in the URL, resolved server-side. See
`docs/architecture.md` for how this differs from the guard stack every
internal controller uses.

## URL shape

| Route | Purpose |
|---|---|
| `GET /p/:stableId` | Product public page. `stableId` is a `Product.stableId`. |
| `GET /u/:stableId` | Unit public page. `stableId` is a `Unit.stableId`. |
| `GET /p/:productStableId/publications/:publicationStableId/download` | Download a specific publication's file, scoped to a product context. |
| `GET /u/:unitStableId/publications/:publicationStableId/download` | Same, scoped to a unit context. |

`publicationStableId` is a `Publication.stableId` — **never** a
`documentRevisionId`, and never a raw storage key. These four routes are
mounted outside the global `/api` prefix (see
`src/common/global-prefix.ts`, shared by `main.ts` and every e2e spec that
boots its own Nest app, so the exclusion list can't silently drift out of
sync between production and tests).

QR codes themselves are generated by the **internal, authenticated** API —
`GET /api/products/:id/qr.svg` / `.png` and `GET /api/units/:id/qr.svg` /
`.png` (Viewer role or higher) — and encode *exactly* the public page URL
above (`${PUBLIC_BASE_URL}/p/{stableId}` or `/u/{stableId}`), nothing else.
No revision, no internal database id, no serial number is embedded — per
spec §32, a printed QR code must never need reprinting just because a
document changed.

## What's exposed vs. what's hidden

The public DTOs are hand-built allowlists (`src/public/dto/public-dtos.ts`),
not "the Prisma row minus some fields" — that's a deliberate choice: it's
easy to audit exactly what a public visitor can see, and adding a field to
an internal model can never accidentally leak it through here.

**Exposed** (product page): product name, model designation, description,
and per resolved publication: document name, document type, revision label,
language, file size, MIME type, sanitized filename, and a download URL
containing only the publication's stableId.

**Exposed** (unit page): everything above, plus the unit's variant name (if
any) and **serial number**. The serial number is intentionally public — spec
§31: it's how the person holding the physical unit confirms the QR they
scanned matches the unit in front of them.

**Never exposed, anywhere in the public response body**: internal database
ids (`Product.id`, `Unit.id`, `DocumentRevision.id`, `Publication.id`), the
storage key/path, a raw storage URL, which organization owns the data, or
anything about *why* a document did or didn't resolve. A stableId that
doesn't exist, belongs to a suspended organization, or belongs to a real
product/unit but has no applicable publications all produce the same shape
of response (200 with an empty `publications` array, or a generic 404 if
the stableId itself doesn't resolve) — there's no signal an outside caller
can use to distinguish "this doesn't exist" from "this belongs to another
tenant" from "this org is suspended."

## Resolution: reusing the one resolver, not a second one

Both pages call `PublicationResolverService.resolvePublications()` — the
exact same function `GET /api/publications/resolve` uses internally — with
`effectiveAt: new Date()` (always "now" for a public visitor; there is no
public historical-resolution feature). This is the single place in the
codebase that decides "what applies here," so a DRAFT, IN_REVIEW, or
APPROVED-but-never-published `DocumentRevision` can never appear publicly:
the resolver only reads `Publication` + `PublicationSnapshot`, never live
`DocumentRevision.status`. A RETIRED revision that was never published
behaves the same way. A REVOKED publication disappears from resolution
(and therefore from the public page) the instant `revokedAt` is set — no
caching layer sits between the resolver and the response.

Live `Product`/`Unit` rows are read only for **identity** (which
product/variant/batch a unit belongs to, its name, its serial), exactly the
same restriction the resolver's own `buildUnitContext()` already documents
for the internal path — never to decide applicability.

## Conflict-hiding decision (spec §79)

If `resolvePublications()` returns entries in `conflicts` (two candidate
revisions tied for the same document+language slot — see
`docs/applicability-resolution.md`), the public pages **drop that entire
resolution-key group** rather than showing anything about the ambiguity.
Spec §79 is explicit that conflict-resolution UX is not meant to be surfaced
to anonymous end users — a public visitor has no way to act on "there are
two candidate revisions, pick one" and showing it would just be confusing
or, worse, expose that the manufacturer's applicability data has an
unresolved authoring mistake. The conflict is still logged server-side
(`PublicService`'s logger, tagged `PublicAccess`) so it isn't silently lost —
an internal user investigating "why isn't my document showing publicly"
still has a paper trail; it just isn't the public HTTP response.

## Download re-validation

Both download routes **re-run `resolvePublications()` from scratch** on
every request — they never trust that a link handed out on a previous page
load is still good. Concretely: look up the `Publication` by
`(stableId, organizationId)` scoped to the product/unit's own
`organizationId`, resolve the product/unit context again, and only stream
the file if that publication's id is still present in the resolved set.
A publication revoked between the time a visitor loaded the page and the
time they click "download" gets a 404, not the file — this is covered by
`apps/api/test/public-access.e2e-spec.ts` ("download endpoint re-checks
resolution ... even if the client cached the URL"). The file itself is
streamed via `StorageService.get(snapshot.storageKey)` — the storage key
never appears in any response header or body; only a sanitized version of
the stored `filename` appears in `Content-Disposition`.

## Rate limiting

`@nestjs/throttler`'s `ThrottlerGuard` is applied only to `PublicController`
(`src/public/public.module.ts`), configured at **30 requests per minute per
IP**. Rationale: a real QR scan is one page load plus a handful of
asset/download requests within a few seconds — 30/min comfortably covers
someone reloading the page or opening several publications from one device,
while still bounding naive scraping/enumeration of stableIds from a single
source. This is registered via `ThrottlerModule.forRoot(...)` **inside**
`PublicModule`, not globally via `APP_GUARD` in `AppModule` — so it does not
apply to the authenticated internal API, which is already gated by JWT +
tenant membership and doesn't need the same protection.

## Tenant isolation without a tenant header

There is no `X-Organization-Id` header on any public route, and nothing a
caller supplies is trusted as an organization identifier. Every lookup
starts from the stable ID in the path (`Product.stableId` or
`Unit.stableId`), and the `organizationId` used for every subsequent query —
including the resolver call — comes from **that row's own
`organizationId`** column, never from the client. There is structurally no
way to request "Org A's product, but resolve it against Org B's
publications," because the organizationId used to scope the resolver call
is derived from the row that was just looked up, not passed in independently.
